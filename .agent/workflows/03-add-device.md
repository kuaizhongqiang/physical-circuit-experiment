# 03 新增 / 修改一个元器件类型

读者：AI
类型：流程
权威：动器件表时的工作顺序（这是最容易返工的一类改动）
状态：2026-11-03 建立
依赖：`../../docs/domain-model.md`（契约）、`../../docs/api.md` §2.4、`../../docs/demo.md` §3.4

## 1 为什么器件改动的返工最贵

一个器件同时牵动**五处**，漏任何一处都会让两端不一致：

```
domain-model.md §2（接点表）   ← 契约真源
domain-model.md §4（典型参数）
api.md §2.4（params 语义） ＆ §3（state_bits 位序）
core::device（支路展开）＋ core::consts（若有新阈值）
demo.md §3.4（接点几何，仅演示页用到的器件必须补）
```

## 2 顺序（不许倒）

1. **先改 `docs/domain-model.md` §2**：接点表（编号、顺序、含义）＋ 支路展开说明 ＋ 状态来源归入 §5 三分类之一。
2. **再补 §4 教学典型值**：给出可算的数值，并顺手推出一个可断言基线（写进 `verification.md`）。
3. **同步 `docs/api.md`**：`params[8]` 逐位语义 ＋ `state_bits` 位序 ＋ 若新增错误条件则加码。
4. **改 `core::device`**：`terminal_count()`、支路展开、参数校验。
5. **补 `demo.md` §3.4 的 (边,u,v)**：仅当演示页会画到该器件。
6. **补 fixture**：至少一个用到该器件的案例 ＋ 一条反例（参数越界或触点状态错）。

## 3 判据

- `pcx_terminal_count(kind, aux)` 与 `domain-model.md` §2 的接点数**逐项相符**（写个表驱动测试，别手数）。
- `state_bits` 位序与 `api.md` §3 一致（同一位对应同一触点，不许"实现里改了顺序文档没改"）。
- 参数越界能返回 `E_PARAM_RANGE`，且诊断能指到 `device_id`。
- 该器件参与的那个案例断言全绿。

## 4 高频错误

| 错误 | 后果 |
|---|---|
| 先写 `core::device` 再补文档 | 文档成"事后描述"，接点顺序与实现相反，双端布局全错 |
| 只改 `domain-model.md` 的接点名，没改序号 | 全局 `terminal_base` 前缀和偏移，**所有后续器件的接点 id 集体错位** |
| 忘了 `terminal_base` 的前缀和 | 表现为"某几个接点结果永远是 0"，极难定位 |
| 触点状态位序与接点顺序混为一谈 | 接点顺序含线圈与热元件，`state_bits` 不含，两者天然不同 |

## 5 不要做的事

- 不要为"以后可能要"的器件预留参数位或接点位 —— 结构体布局一旦定就是契约。
- 不要新增器件却复用别家的 `kind` 编号；`kind` 只许追加，不许重排。
